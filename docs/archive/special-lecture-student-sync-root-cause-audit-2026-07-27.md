# 특강 학생별 시간 동기화 근본원인 감사 - 2026-07-27

## 결론

신초봄의 4·5회차 시간 변경을 막은 기록은 신초봄 것이 아니라 김연우 것이었다. 데이터가 학생 간에 섞인 것은 아니며, 프론트의 보호 조건이 `lessonId`만 비교해 같은 수업의 모든 학생 기록을 하나의 잠금으로 취급한 것이 직접 원인이다.

하지만 직접 조건만 고치는 것으로는 충분하지 않았다. 학생 한 명의 시간 변경이 명단 제거 시 기록 삭제·알림 취소 부작용을 가진 범용 `/api/lessons/bulk`를 통해 수업 전체 row를 저장하고 있었기 때문이다. 오래된 화면 상태가 다른 학생의 최신 변경을 덮을 가능성도 있었다.

## 오류가 들어온 경위

- 도입 커밋: `3ffdeb1e0` (`Sync special lecture times to future journals`, 2026-07-23)
- 당시 목표: enrollment 회차 계획을 저장한 뒤 미래 lessons의 학생별 시간도 함께 맞춘다.
- 당시 안전 규칙: 오늘/과거, 완료 수업, `lesson_student_records`가 하나라도 있는 수업, 대기 알림이 있는 수업은 모두 잠근다.
- 계약 불일치:
  - 실제 변경 범위: 학생 한 명의 명단 포함 여부와 학생별 시간
  - 보호 판정 범위: 수업 전체
  - 서버 저장 범위: 수업 전체 row
- 자동검증 공백: production 시나리오는 `hasRecords` 같은 코드 문자열의 존재를 확인했지만, 같은 수업에 김연우 기록과 신초봄 시간 변경이 동시에 있는 2학생 실행 fixture가 없었다.
- UI 공백: 카드 완료 표시는 학생 ID 포함 여부만 확인하고 학생별 시작·종료·공식/조정 유형·사유는 비교하지 않았다.

## 서버 부작용 확인

`api/routes/coreData.js`의 일반 lesson 저장은 명단 변경 뒤 다음 작업을 자동 실행한다.

1. 명단에서 빠진 학생의 대기 `notification_jobs` 취소
2. 명단에서 빠진 학생의 `lesson_student_records` 삭제

따라서 명단 제거에는 학생 기록 보호가 반드시 필요하다. 반면 학생을 유지한 시간 변경은 기록을 삭제하지 않으므로 다른 학생의 기록이나 대상 학생의 기존 기록을 잠금 근거로 사용할 이유가 없다. 대기 알림은 문구의 시간이 낡을 수 있으므로 대상 학생의 알림만 보호해야 한다.

## 적용한 최종 계약

- 변경 종류를 `none/add/update/remove`로 먼저 분류한다.
- 오늘/과거와 완료 수업은 모든 자동 변경을 보호한다.
- `remove`일 때만 대상 학생의 record 존재 여부를 보호 사유로 사용한다.
- 알림은 대상 학생의 pending job 또는 학생 ID가 없는 수업 공통 job만 보호한다. 다른 학생 job은 차단하지 않는다.
- 기존 lesson의 학생별 변경은 범용 bulk 저장을 사용하지 않는다.
- 전용 API가 Supabase 최신 lesson을 다시 읽고 대상 학생만 병합한다.
- `updated_at` compare-and-swap 조건으로 다른 탭의 선행 변경을 덮어쓰지 않는다.
- PATCH 대상은 `student_ids`, `special_lecture_student_schedules`, `updated_at`뿐이다.
- 범용 bulk의 수업 전체 알림 취소·record 정리 후처리도 호출하지 않는다. 대상 학생 제거는 대상 학생 record·pending job이 없을 때만 허용되므로 별도 정리 부작용이 필요 없다.
- 응답과 전체 lessons 재조회에서 대상 학생 일정이 계획과 일치해야만 완료한다.
- 기존 lesson이 없는 신규 회차만 범용 bulk 생성 경로를 사용한다.

## 실행형 회귀 fixture

`scripts/test-special-lecture-plan-sync.mjs`는 다음을 직접 실행한다.

1. 김연우 결석과 김연우 대기 알림이 있어도 신초봄 시간 변경은 허용
2. 신초봄 시간 변경 뒤 김연우 시간·수업 명단·기타 lesson 필드 보존
3. 신초봄 본인 record가 있어도 명단을 유지하는 시간 변경은 허용
4. 신초봄을 명단에서 제거할 때 신초봄 record가 있으면 차단
5. 신초봄 본인의 대기 알림이 있으면 차단
6. 오늘/과거와 완료 수업은 차단
7. 저장 뒤 신초봄 일정이 확정 계획과 정확히 일치

이 테스트는 `npm run test:production`에 포함돼 이후 조건을 다시 수업 전체 범위로 넓히면 실패한다.

## `/api/lessons/bulk` 호출 전수 목록

| 호출 경로 | 변경 범위 | 현재 저장 확인 | 확인된 위험 | 후속 gate |
|---|---|---|---|---|
| 특강 신규 수업 생성 | 존재하지 않는 신규 lesson | 저장 후 전체 lessons 재조회 | 기존 record가 없는 신규 row에 한정 | 유지 |
| 특강 기존 학생별 시간 | 학생 1명 | 전용 API + CAS + 전체 재조회 | 이번 작업에서 bulk 사용 제거 | 완료 |
| 자동 생성 수업 저장 | 생성·전체 row 갱신 | 응답 반영, 전체 재조회 없음 | 오래된 row·명단 덮어쓰기 가능 | 생성 수업 저장 gate |
| 수업 생성·수정 모달 | 사용자가 편집한 전체 row | 전체 재조회 있음 | 명단 제거 시 record 삭제 사전 안내 부족 | 수업 수정/취소 gate |
| 학생 반 이동·퇴원 미래 명단 자동정리 | 여러 미래 lesson 명단 | 낙관적 화면 변경, 재조회 없음 | record 삭제·알림 취소와 실패 시 화면/서버 불일치 가능 | 학생/반 명단 P0 gate |
| Tally 학생 등록 후 미래 명단 반영 | 이전/새 반 미래 lesson 명단 | 전체 재조회 있음 | 이전 반 제거 대상 record 사전 보호 없음 | 학생/Tally P0 gate |
| 시험대비 lesson reconcile | 전체 row 저장·lesson 삭제 | 낙관적 변경, 재조회 없음 | record·homework·알림과 함께 삭제될 수 있음 | 시험대비 저장 gate |

같은 `lessonId`만 보는 record 잠금 조건은 특강의 전체 회차 미리보기 한 곳에도 남아 있다. 이 경로는 학생 한 명 변경이 아니라 전체 enrollment 원천으로 lesson 전체 명단·시간을 재구성하므로 수업 전체 잠금이 맞다. 기록이 있어도 기존 학생·시간을 그대로 보존하고 누락 학생만 추가하는 경우에는 별도 additive-only 확인 gate를 사용한다.

## 운영 데이터 경계

이번 근본원인 감사·코드 변경·자동검증은 운영 enrollment, lessons, 수업일지, 김연우 결석, 신초봄 학생별 시간, notification job, Solapi를 수정하지 않는다. 신초봄 4·5회차 실제 시간 반영은 배포 후 교사가 회차 모달의 2단계를 실행할 때만 발생한다.
