# 반복 렌더(행·카드)의 액션 배치 규칙

표의 행이나 목록의 카드처럼 **같은 모양이 N번 반복되는 자리**에 액션 버튼을 어떻게 놓을지에 대한 규칙이다.
버튼의 *종류*(primaryButton/softButton/…)는 `docs/ui-button-hierarchy.md`가 정하고, 이 문서는 그 버튼을
*어디에 몇 개* 놓을지를 정한다.

## 왜 필요한가

40행짜리 학생 목록에서 행마다 `저장`(대부분 비활성)과 `퇴원`(빨간 버튼)이 반복되면,

- 비활성 버튼 40개가 시선을 끌면서 아무 일도 하지 않는다.
- 빨간 버튼이 스크롤 내내 반복되면 위험 신호가 마모되고(경고 피로), 오클릭 위험은 오히려 커진다.
- 정작 중요한 데이터(이름·반·연락처)가 액션 열에 밀려 좁아진다.

## 규칙

### R1. 반복 렌더 안에서 비활성 액션 버튼을 렌더하지 않는다

행/카드 안의 버튼은 **지금 누를 수 있을 때만** 존재해야 한다. `disabled`로 깔아두지 말고,
조건부로 렌더하지 않거나 다른 곳(저장 바/오버플로 메뉴)으로 옮긴다.

### R2. 편집 가능한 표·리스트는 행별 저장 버튼 대신 `StickySaveBar` 하나로 모은다

- 변경된 행은 **하이라이트로만** 표시한다(예: `.dirtyStudentRow`).
- 저장 바 문구는 `N개 행 변경됨`, 액션은 `[모두 저장]`, `[되돌리기]`.
- 저장 상태는 `StickySaveBar`가 내부에서 `InlineSaveStatus`로 그린다. 행마다 상태 뱃지를 따로 두지 않는다.
- 여러 행의 상태를 하나로 합칠 때는 `getAggregateSaveState`를 쓴다(직접 우선순위를 재구현하지 않는다).
- **부작용이 있는 필드는 자동저장으로 바꾸지 않는다.** 예를 들어 학생의 반 변경은 미래 수업 명단까지
  바꾸므로(`previousClassTemplateId` + `rosterEffectiveMode`), 적용 시점 선택은 행 안에 남기고
  저장은 여전히 명시적 행동이어야 한다. 단순 필드(전화번호/학교/PIN)와 부작용 필드를 구분해 설계한다.

### R3. 파괴적이고 저빈도인 액션은 행 끝 오버플로(⋯) 메뉴로 접는다

대상: 퇴원, 삭제, 전체 취소, 인수인계, 영구삭제처럼 **되돌리기 어렵고 자주 쓰지 않는** 액션.

- `src/shared/components/OverflowMenu.jsx`를 쓴다.
- 파괴적 항목은 `tone="danger"`로 구분한다.
- 확인 모달이 이미 있는 액션은 모달을 그대로 유지한다(메뉴는 진입점만 옮기는 것이지 확인 단계를 없애지 않는다).
- 접근성: 메뉴가 그 액션의 **유일한 진입점**이면 트리거 `aria-label`에 대상 이름을 포함한다
  (예: `${student.name} 추가 작업`). 스크린리더에서 "더보기"가 40개 나열되면 안 된다.

### R4. 리피터(폼 배열) 행의 제거는 아이콘 버튼(×)으로 한다

"항목 추가/제거"로 배열을 편집하는 폼(개별 스케줄, 회차 목록 등)에서 제거는 텍스트 `삭제` 버튼이 아니라
`iconButton` + `aria-label`로 한다. 선례: `SchoolCalendarComponents.jsx`의 리피터 행.

**리피터는 R2·R3의 대상이 아니다.** 리피터의 제거는 저장 전 초안을 되돌리는 편집 동작이지
저장된 데이터를 파괴하는 액션이 아니다. 성격이 다르므로 규칙을 섞지 않는다.

### R5. 다중 선택이 유용한 표는 `SelectionToolbar`를 쓴다

선택 후 일괄 처리가 자연스러운 목록(퇴원생 목록 등)은 행별 액션 대신 선택 + 툴바로 간다.
안전한 액션은 `actions`, 파괴적 액션은 `dangerActions`로 나눠 넘긴다.

### R6. 저장 상태 문구는 `saveStateLabels` 밖의 새 문자열을 만들지 않는다

`idle/dirty/saving/verifying/saved/failed` 6종이 전부다. "저장됨", "재시도" 같은 화면 전용 변형을
새로 만들지 않는다. 문구가 부족하면 `InlineSaveStatus.jsx`에서 공용으로 고친다.

## 적용 여부 판단표

| 상황 | 규칙 |
| --- | --- |
| 표의 셀을 직접 편집하고 행마다 저장 버튼이 있다 | R2 |
| 행/카드마다 빨간 삭제·퇴원 버튼이 있다 | R3 |
| 폼 안에서 `+ 추가`로 늘리는 배열의 행 제거 | R4 (R2·R3 아님) |
| 여러 건을 한 번에 처리하는 게 흔하다 | R5 |
| 행마다 액션이 1개뿐이고 파괴적이지 않다 | 그대로 둔다 (예: `상세 관리`) |

## 기준이 되는 구현

- `src/domains/students/StudentManager.jsx` — 액티브 학생 목록. R1·R2·R3의 레퍼런스.
- `src/domains/exams/ExamPrepCenter.jsx` — 셀은 읽기 전용, 행당 액션 1개, 상태는 `InlineSaveStatus`.
- `src/domains/students/StudentWithdrawnList.jsx` — R5의 레퍼런스.
- `src/domains/schoolCalendar/SchoolCalendarComponents.jsx` — R4의 레퍼런스.
